## Вердикт: Система работает правильно

### Почему это НЕ ошибка

1. **431 продажа за 5 минут физически невозможна**
   - Слежение за остатками работает с интервалом ~5 минут
   - Даже очень активный магазин не продаёт 86 книг в минуту
   - Это 1.48% каталога — явный признак сбоя API

2. **Типичные причины массового обнуления остатков:**
   - Временная недоступность склада WB
   - Неполный ответ API (обрыв пагинации)
   - Лимит запросов к API
   - Технический сбой на стороне Wildberries

3. **Предохранитель защитил от катастрофы:**
   - Без него 431 книга была бы снята с ОБЕИХ площадок (Ozon + WB)
   - Восстановление потребовало бы ручной работы
   - Через 10 минут ситуация повторилась бы

## Что делает система

### Три уровня защиты от ложных снятий

1. **Опрос заказов (каждую минуту)**
   - Работает по API заказов, не по остаткам
   - Поймает ВСЕ реальные продажи
   - Не зависит от состояния складов

2. **Слежение за остатками (каждые 5 минут)**
   - Быстро реагирует на изменения
   - Имеет предохранитель MAX_WATCH_REMOVALS_PER_RUN = 10
   - При массовом обнулении останавливается и пишет в журнал

3. **Полная сверка каталога (каждый час)**
   - Авторитетный источник истины
   - Тянет весь каталог целиком
   - Имеет свой предохранитель MAX_SYNC_REMOVALS_PER_RUN = 50

### Как обрабатываются реальные продажи

```
Продажа на WB
   ↓
1. Опрос заказов (1 мин) → создаёт Order → снимает книгу с обеих площадок
   ИЛИ
2. Слежение (5 мин) → видит остаток 0 → снимает (если < 10 книг за проход)
   ИЛИ
3. Полная сверка (60 мин) → книга пропала из каталога → снимает
```

**Вывод:** Ни одна реальная продажа не теряется, даже если watch_stocks остановился.

## Что было исправлено

### До исправления

Полный список 431 книги НЕ сохранялся — в журнале были только первые 10 SKU.

### После исправления

```python
# catalog_sync.py:586
if len(candidates) > MAX_WATCH_REMOVALS_PER_RUN:
    skus_sample = ", ".join(b.sku for _, b, _ in candidates[:10])
    all_skus = ", ".join(b.sku for _, b, _ in candidates)
    
    # Краткое сообщение для UI

    # Полный список в отдельной записи

```

Теперь при следующем срабатывании:
1. В журнале будет краткое сообщение для UI (первые 10 SKU)
2. В журнале будет полный список всех затронутых книг
3. Скрипт `scripts/halted_stocks_report.py` покажет оба списка

## Нужно ли что-то делать?

### НЕТ, если это разовое срабатывание

- Предохранитель работает правильно
- Реальные продажи обрабатываются другими механизмами
- Следующий проход слежения (через 5 минут) всё исправит

### ДА, если срабатывания частые (несколько раз в день)

1. **Проверить API Wildberries**
   - Возможно, проблемы с их инфраструктурой
   - Проверить статус на https://seller.wildberries.ru/

2. **Проверить лимиты запросов**
   - fetch_stocks может упираться в rate limit
   - Увеличить интервал stock_watch_interval_minutes в config.py

3. **Рассмотреть увеличение порога** (крайняя мера)
   ```python
   # catalog_sync.py:71
   MAX_WATCH_REMOVALS_PER_RUN = 20  # было 10
   ```
   ⚠️ Осторожно: выше порог = выше риск массового ложного снятия
