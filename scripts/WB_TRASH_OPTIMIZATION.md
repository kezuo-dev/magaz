# Оптимизация удаления карточек в корзину WB

## Проблема

Система не справляется с большим потоком продаж — книги накапливаются в "буфере" (БД) и не удаляются в корзину WB.

### Старая реализация

```python
# scheduler.py
move_withdrawn_to_trash(db, hours=3, verbose=False)

# wb_trash.py
BATCH_SIZE = 5
PAUSE_SECONDS = 5
```

**Окно 3 часа:**
- Обрабатываются только книги `updated_at >= now() - 3 часа`
- Книга старше 3 часов **пропадает из выборки навсегда**
- При потоке > 30 книг/час backlog растёт без границ

**Производительность:**
- Пачка: 5 карточек
- Пауза: 5 секунд
- Запуск каждые: 10 минут
- **Максимум: 30 карточек/час = 720/день**

### Почему накапливался backlog

```
10:00 — Продано 50 книг
10:10 — Scheduler: берём книги за последние 3 часа (07:10-10:10)
        → Нашли 50 книг
        → Удалили 5 (первая пачка)
        → Лимит 429 → STOP
        → Отложено 45 книг

10:20 — Scheduler: берём книги за последние 3 часа (07:20-10:20)
        → Нашли те же 45 + новые 8 = 53
        → Удалили 5
        → Лимит 429 → STOP

... каждые 10 минут удаляем по 5, но продаётся больше ...

13:10 — Scheduler: берём книги за последние 3 часа (10:10-13:10)
        → 45 книг из 10:00 ПРОПАЛИ (старше 3 часов)
        → Они больше НИКОГДА не попадут в выборку
        → Backlog = 45 + 45 + 45 + ... → бесконечность
```

**Фатальная ошибка:** Скользящее окно отбрасывает необработанные книги.

## Оптимизация

### 1. Убрано окно 3 часа → FIFO-очередь

```python
# wb_trash.py:83-93
query = (
    select(Book)
    .options(selectinload(Book.listings))
    .where(
        Book.status.in_([BookStatus.SOLD, BookStatus.WITHDRAWN]),
        Book.listings.any(Listing.marketplace == "wildberries"),
    )
    .order_by(Book.updated_at.asc())  # FIFO: старые книги первыми
    .limit(MAX_BOOKS_PER_RUN)          # берём порцию, не зависаем
)
```

**Преимущества:**
- Все снятые книги попадают в выборку
- Старые книги обрабатываются первыми
- Backlog постепенно рассасывается
- Нет потерянных книг

### 2. Увеличены пачки: 5 → 30

```python
BATCH_SIZE = 30  # было 5
```

API WB принимает массив `nmIDs` — нет смысла слать по 5 штук.

### 3. Уменьшена пауза: 5с → 2с

```python
PAUSE_SECONDS = 2  # было 5
```

2 секунды достаточно, чтобы API остыл. Не жертвуем надёжностью, ускоряем обработку.

### 4. Лимит MAX_BOOKS_PER_RUN = 100

```python
MAX_BOOKS_PER_RUN = 100
```

Защита от зависания scheduler'а: если backlog огромный (тысячи книг), не обрабатываем всё за раз — берём порцию 100 штук (~3 минуты работы), остальное в следующий запуск.

### 5. Улучшено логирование

```python
# Было
_log(..., message=f"Карточка {nm} удалена в корзину WB")

# Стало
_log(..., book_id=book.id, message=f"Карточка {nm} ({book.sku}) удалена в корзину WB")
```

Теперь в журнале видно SKU книги, не только nmID.

## Новая производительность

### Теоретический максимум

```
Пачка: 30 карточек
Пауза: 2 секунды
Время на пачку: ~2 секунды

За 10 минут (интервал запуска):
  Пачек: 100 / 30 ≈ 4 пачки
  Время: 4 × 2с = 8 секунд
  Карточек: 100 (limit)

За час:
  Запусков: 6
  Карточек: 100 × 6 = 600 (если всё время есть что удалять)

За день:
  Карточек: 600 × 24 = 14 400
```

### Реальная скорость (с учётом лимитов WB)

API WB может останавливать на 429. Консервативная оценка:

```
За час: 180-300 карточек
За день: 4 320-7 200 карточек
```

**Ускорение в 6-10 раз** по сравнению со старой системой (720/день).

## Сценарии работы

### Сценарий 1: Нормальный поток (10 продаж/час)

```
10:00 — Продано 10 книг
10:10 — Scheduler: нашли 10, удалили 10 за 1 пачку (4 сек)
        → Backlog = 0 ✓

10:20 — Scheduler: нашли 2 новые, удалили 2
        → Backlog = 0 ✓
```

**Вывод:** Справляется легко, backlog не растёт.

### Сценарий 2: Высокий поток (50 продаж/час)

```
10:00 — Продано 50 книг
10:10 — Scheduler: нашли 50, удалили 30 (1 пачка), лимит 429
        → Backlog = 20

10:20 — Scheduler: нашли 20 старых + 8 новых = 28
        → Сортировка по updated_at ASC: сначала 20 старых
        → Удалили 28 за 1 пачку
        → Backlog = 0 ✓

10:30 — Scheduler: нашли 8 новых, удалили 8
        → Backlog = 0 ✓
```

**Вывод:** Backlog рассасывается за 1-2 прохода, старые книги не теряются.

### Сценарий 3: Очень высокий поток (100 продаж/час)

```
10:00 — Продано 100 книг
10:10 — Scheduler: limit=100, нашли 100, удалили 30, лимит 429
        → Backlog = 70

10:20 — Scheduler: нашли 70 старых + 17 новых = 87
        → Берём 87 (старые первыми)
        → Удалили 60 (2 пачки), лимит 429
        → Backlog = 27 + 17 новых = 44

10:30 — Scheduler: нашли 44 старых + 17 новых = 61
        → Удалили 60
        → Backlog = 1 + 17 новых = 18

10:40 — Scheduler: нашли 18 старых + 17 новых = 35
        → Удалили 30
        → Backlog = 5 + 17 новых = 22

... постепенно рассасывается ...
```

**Вывод:** Даже при очень высоком потоке (100/час) backlog не растёт бесконечно — система постепенно догоняет, обрабатывая старые книги первыми.

### Сценарий 4: Огромный accumulated backlog (1000 книг)

```
10:00 — В БД 1000 снятых книг (накопилось за месяц)
10:10 — Scheduler: limit=100, берём 100 самых старых
        → Удалили 60, лимит 429
        → Осталось в backlog: 1000 - 60 = 940

10:20 — Scheduler: берём следующие 100 самых старых
        → Удалили 60
        → Осталось: 880

... каждые 10 минут убираем 30-60 книг ...

Через 5 часов: backlog = 0 ✓
```

**Вывод:** Даже огромный accumulated backlog постепенно рассасывается. Система НЕ зависает (limit=100), НЕ теряет старые книги (FIFO).

## Что делать, если всё равно не справляется

### 1. Увеличить частоту запуска

```python
# config.py
wb_trash_interval_minutes = 5  # было 10
```

Запусков в 2 раза больше → производительность в 2 раза выше.

### 2. Увеличить размер пачки (осторожно)

```python
# wb_trash.py
BATCH_SIZE = 50  # было 30
```

⚠️ Может увеличить частоту 429. Тестировать постепенно.

### 3. Увеличить limit за проход

```python
# wb_trash.py
MAX_BOOKS_PER_RUN = 200  # было 100
```

⚠️ Scheduler будет дольше занят (до 6 минут). Приемлемо, если интервал 10 минут.

### 4. Проверить лимиты WB

Возможно, API WB имеет дневной/часовой лимит на DELETE. Свяжитесь с поддержкой WB.

## Мониторинг

### SQL: Текущий размер backlog

```sql
SELECT COUNT(*) as backlog
FROM books
WHERE status IN ('sold', 'withdrawn')
  AND EXISTS (
    SELECT 1 FROM listings 
    WHERE listings.book_id = books.id 
      AND listings.marketplace = 'wildberries'
  );
```

### SQL: Динамика за последние 24 часа

```sql
SELECT 
    DATE_TRUNC('hour', created_at) as hour,
    COUNT(*) as deleted
FROM sync_log
WHERE action = 'wb_trash'
  AND ok = TRUE
  AND message LIKE '%удалена в корзину%'
  AND created_at >= NOW() - INTERVAL '24 hours'
GROUP BY hour
ORDER BY hour;
```

### SQL: Частота лимитов 429

```sql
SELECT 
    DATE(created_at) as date,
    COUNT(*) as hit_limit_times
FROM sync_log
WHERE action = 'wb_trash'
  AND message LIKE '%Лимит WB%'
  AND created_at >= NOW() - INTERVAL '7 days'
GROUP BY date
ORDER BY date DESC;
```
